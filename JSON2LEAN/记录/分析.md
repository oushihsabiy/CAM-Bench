# JSON2LEAN 形式化错误分析

## 统计口径

本文采用 4 类形式化错误与 6 个数学领域进行交叉分析。需要区分两层信息：

1. **Observable failure mode**：日志中直接可见的失败现象，例如 `exact?`、remaining `sorry`、compile error、`compile_stuck`、LLM budget exceeded。
2. **Inferred failure cause**：根据日志、summary、proof artifact 和题目内容推断出的主要失败原因，即 E1-E4。

为避免把表面现象误当作根因，本文推荐以下口径：

- Aristotle / Agent：`exact?` 单独列为 proof-artifact / validation uncertainty，不直接混入 causal failure 主表。
- pass@k：`compile_stuck` 不默认等于 E2。只有存在明确的 Lean 类型/API/side-condition 失败证据时归入 E2；若只是多轮 repair 后无法关闭，则归入 E4。
- pass@k 主表使用 **unique-source** 口径，而不是 block-run 口径。block-run 会把同一题在多个模型、多个 proof block 上的失败重复放大。

## 错误类型

| 编号 | 名称 | 核心含义 |
|---|---|---|
| E1 | Library and Infrastructure Gaps | 形式化库或应用数学基础设施不足，或者现有 Mathlib 接口难以直接支撑证明 |
| E2 | Formal Representation and Type Discipline | 数学对象进入 Lean 类型系统时失败，包括类型、维度、索引、coercion、typeclass、side conditions |
| E3 | Statement and Proof-Artifact Fidelity | 返回的证明 artifact 不符合评测契约，或改变了 fixed statement / definition / 证明了相近命题 |
| E4 | Proof Decomposition and Long-Horizon Control | 长证明拆解、辅助引理设计、多轮 repair、budget 控制、proof-state 管理失败 |

### Agent：解释

Agent 的真实 causal failure 不是 E3 占主导，而是 E1 占主导。原因是许多失败 summary 明确指出 Mathlib 或应用数学基础设施不足，例如谱分解、矩阵不等式、Farkas 型结果、Prékopa-Leindler、Pick/Nevanlinna 等基础结果缺失或难以调用。

E2 主要来自编译错误、类型不匹配、索引/维度/coercion/typeclass 管理失败。E4 主要来自长证明中已构造若干辅助引理但最终关键目标无法关闭，或者 job failed / budget exhausted。

这个表是最可靠的 pass@k 原始统计。但它不是 E1-E4 根因统计，因为 `compile_stuck` 可能由 E1、E2、E4，甚至 E3 引起。

### pass@k causal failure 主表

pass@k 的主表推荐使用 unique-source 口径，分母为 `712` 个 unique failed source problem。

采用保守映射：

- 明确缺库、深层 Mathlib / 应用数学基础设施缺口：E1。
- 明确类型、索引、维度、coercion、typeclass、side condition 编译失败：E2。
- malformed proof block、markdown fence、`admit/sorry` artifact、proof artifact 不符合评测契约：E3。
- 没有明确局部 type-error 证据，但多轮 repair 后卡住、LLM error、budget/limit exceeded：E4。

| 错误类型 | 数量 | 占比 |
|---|---:|---:|
| E2 Formal Representation and Type Discipline | 252 | 35.4% |
| E4 Proof Decomposition and Long-Horizon Control | 224 | 31.5% |
| E1 Library and Infrastructure Gaps | 182 | 25.6% |
| E3 Statement and Proof-Artifact Fidelity | 54 | 7.6% |

该表比直接把大多数 `compile_stuck` 归入 E2 更合理。它反映了 pass@k 中的三类主要瓶颈：Lean 表达/类型纪律、长程 repair 控制、以及 Mathlib/基础设施缺口。

## 综合结论

Agent 与 pass@k 的错误结构不同。

Agent 的 causal failure 中，E1 是最大类。这说明 Aristotle 在难题上常常能推进一部分证明，但最终卡在 Mathlib 或应用数学基础设施不足上，尤其是谱矩阵、PSD/PD、特征值、log-det、trace、矩阵不等式、凸几何基础定理等内容。

pass@k 的主要失败来自 E2 和 E4。E2 反映局部 Lean 表达、类型纪律、side conditions 和 API 使用失败；E4 反映多轮 repair、proof-state 管理、辅助引理规划和 budget 控制失败。直接把所有 `compile_stuck` 算成 E2 会使 E2 虚高，因此主表中将无明确 type-error 证据的长期卡住样本部分归入 E4。

E3 在 Agent 中主要体现为 `exact?` 或 proof artifact 需要更严格验证；在 pass@k 中比例较低，但仍然存在 malformed artifact、markdown fence、`admit/sorry` 等问题。因此 E3 保留是合理的，但不应让 `exact?` 淹没 causal failure 主表。

领域上，谱与矩阵推理最突出的问题是 E1，凸性与几何不等式更容易触发 E2/E4，优化建模与对偶则同时受到 E2、E4、E1 影响。应用建模、算法收敛、最优性条件三个领域样本相对较少，更适合作为补充观察。

## 推荐论文表述

建议主文中报告：

1. Agent 表：报告 `exact? = 28` 作为 validation uncertainty；causal failure 主表使用剩余 `37` 个 hard failures。
2. pass@k 表：先报告 observable failure modes；E1-E4 主表使用 `712` 个 unique failed source problem。
3. block-run 口径只作为补充，说明原始 failed block-run 为 `1802`，其中 `compile_stuck` 为 `1547`。

推荐表述：

> We separate observable failure modes from inferred causal failure categories. For Aristotle, `exact?` cases are reported separately as proof-artifact or validation uncertainty rather than being treated as ordinary proof failures. Under this causal-failure view, library and infrastructure gaps form the largest Aristotle failure category, especially in spectral and matrix reasoning. For pass@k, most raw failures appear as `compile_stuck`, but this surface signal conflates local Lean type/API failures with long-horizon repair failures. Using source-level deduplication and conservative causal mapping, pass@k failures are primarily split between formal representation/type discipline and proof decomposition/long-horizon control, with library and infrastructure gaps remaining a stable third component concentrated in spectral and matrix problems.
