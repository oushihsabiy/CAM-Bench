# 8 小时限制与 exact? 伪证明改判后的重新分析

生成日期：2026-05-05

## 新评测口径

本报告采用更严格的口径：

1. 只有在 8 小时以内完成的题才算成功。
2. aristotle 人工标记中包含 `exact?` 的题全部按伪证明处理，改判失败。
3. m2f 仍按 `reason_group == done` 且 `minutes_total <= 480` 计成功。
4. m2f 数据中没有类似 aristotle `yes -exact?` 的显式人工伪证明标签；目前只能检查 `sorry/sorryAx`、`bad_statement`、`reason_group`。因此该口径对 m2f 和 aristotle 的可观测标签并不完全对称，这是一个需要在图注或论文中说明的限制。

补充变体：报告末尾也给出“8 小时 + exact? 改判 + `yes -xiu` 修题也不算”的更严格结果，供比较。

与 `/root/workspace/benchmark/JSON2LEAN/记录/精确记录.md` 的关系：该文件末尾的“统计总览”已经采用 `exact? -> no` 规则。因此，若对齐 `精确记录.md` 的最终人工统计，aristotle 不是 164/200，而是所有 yes 类 135/200、8h 以内 yes 类 131/200。本文表格里的“原始主口径成功数 164/200”指的是只按逐题 `人工标记 yes*` 解析、尚未应用 `exact? -> no` 的宽松口径，不能和 `精确记录.md` 的统计总览直接等同。

## 总体结果

| 口径 | m2f | aristotle |
|---|---:|---:|
| 宽松逐题 yes* 口径 | 173 / 200 | 164 / 200 |
| 对齐 `精确记录.md` 的所有 yes 类 | 不适用 | 135 / 200 |
| 仅加 8 小时时间限制 | 147 / 200 | 157 / 200 |
| 8 小时 + exact? 改判失败 | 147 / 200 | 131 / 200 |
| 8 小时 + exact? 改判 + 修题不算 | 147 / 200 | 125 / 200 |

解释：

- m2f 从 173 降到 147，主要是 26 个原本成功的题超过 8 小时。
- aristotle 的 164 是宽松 `yes*` 解析；`精确记录.md` 的最终统计已经把 29 个 `exact?` 归入 no，所以“所有 yes 类”为 135。
- aristotle 从宽松 164 降到 131，包含两类损失：
  - 7 个原本成功但超过 8 小时。
  - 26 个原本 8 小时内成功但带 `exact?` 标记，被改判失败。
- 如果进一步把 `yes -xiu` 修题也不算，aristotle 再从 131 降到 125。

其中 26 个本来在 8 小时以内，会在新口径下由成功改判失败：

3, 5, 8, 10, 18, 27, 57, 61, 69, 83, 87, 92, 97, 103, 104, 119, 130, 134, 135, 143, 145, 153, 181, 182, 190, 195

另外 3 个 `exact?` 题本身已超过 8 小时，因此在时间限制下已经失败：

19, 100, 155

这说明 `exact?` 标记对 8 小时内成功率影响很大：aristotle 的 8 小时成功数从 157 降到 131，正好少 26 题。

## m2f 的 8 小时影响

m2f 原始主口径成功 173 题。加入 8 小时限制后，成功数降到 147 题。被时间限制剔除的 26 个原本成功题为：

7, 14, 58, 59, 73, 88, 111, 125, 140, 150, 151, 153, 154, 155, 156, 157, 158, 159, 162, 163, 169, 170, 171, 172, 173, 175

这些题不是 `sorry` 失败，而是超过 8 小时。这里要注意 m2f 的时间来源混合了 `reported`、`history_log_sum`、`log_sum`，所以超过 8 小时有时代表多轮历史累计，不一定等同于单次 wall-clock。

## 更严格变体：修题也不算

如果进一步把 `yes -xiu` 也算失败，即要求 8 小时内完成、无 `exact?`、且不通过修题完成，则 aristotle 成功数变为 125/200。

8 小时内 `yes -xiu` 的 6 题是：

52, 70, 122, 161, 168, 194

此变体下：

| 集合 | 题数 |
|---|---:|
| m2f 成功 | 147 |
| aristotle 成功 | 125 |
| 两者都成功 | 103 |
| 仅 m2f 成功 | 44 |
| 仅 aristotle 成功 | 22 |
| 至少一个成功 | 169 |
| 两者都失败 | 31 |

这个变体更适合评测“保持原 theorem statement 不变的单题证明能力”；但如果 benchmark 也想测题面审计和修正能力，就不应把 `yes -xiu` 简单丢掉，而应作为单独标签报告。

## 这个口径对 benchmark 是否更有利

我认为更有利，但要用对叙事。

有利之处：

1. 更强调 benchmark 的严肃性：`exact?` 等伪证明不计分，避免把看似成功但证明质量可疑的结果混入 pass rate。
2. 更符合实际使用场景：8 小时预算使结果变成 time-bounded benchmark，而不是无限长尾累计。
3. 更能凸显人工审核价值：aristotle 原先 157 个 8 小时内成功里，有 26 个因 `exact?` 被剔除，说明人工标注能识别 API/status 看不出的伪成功。
4. 更不饱和：至少一个 agent 成功从 184 降到 174，共同失败从 16 增到 26，benchmark 的长期提升空间更明显。
5. 更适合画正确率随时间曲线：曲线不只是最终成功率，还能展示在固定预算内哪些结果是真成功、哪些是伪成功。

需要谨慎之处：

1. 这个口径会明显降低 aristotle 成绩，因为 `exact?` 标签来自人工审核记录；m2f 没有同等粒度的 `exact?` 人工标签，所以不能把差距简单说成模型能力差距。
2. m2f 的 8 小时统计受时间来源影响，`history_log_sum` / `log_sum` 可能把多轮累计时间算到同一题。
3. `yes -xiu` 应独立报告。修题不应和伪证明混为一谈：修题可以是 benchmark 的 statement-audit 能力，而 `exact?` 更像证明质量问题。

推荐论文/报告中的说法：

> Under an 8-hour budget and after excluding exact?-style pseudo-proofs, the benchmark remains far from saturated: the two agents solve 147 and 131 problems respectively, with a union of 174/200 and 26 problems unsolved by both. This stricter protocol highlights the importance of human auditing and time-bounded evaluation, while preserving separate labels for statement repair and false-statement detection.

## 建议画图

建议画两条或三条累计曲线：

1. raw/audited curve：按人工 `yes*`，不剔除 `exact?`，展示原始人工审核通过率。
2. strict curve：8 小时内、`exact?` 改判失败，展示主结果。
3. no-repair curve：再把 `yes -xiu` 也剔除，作为最严格变体。

对 aristotle，可以在图里用虚线显示“包含 exact?”，实线显示“剔除 exact?”。这会直观展示伪证明过滤对 benchmark 结果的影响。

对 m2f，建议单独标注：

- 8 小时内成功：147。
- 超过 8 小时但最终成功：26。
- 无显式 `exact?` 人工标签，因此未做同类伪证明扣分。

这种画法最能凸显 benchmark 的价值：它不是单一排行榜，而是能区分时间预算、证明质量、修题行为、长尾基础设施的诊断工具。
